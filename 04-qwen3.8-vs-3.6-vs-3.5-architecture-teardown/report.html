01Verdict

These three releases are the same machine. 3.5 and 3.6 are tensor-for-tensor identical in structure (same 1,307 tensor names, shapes, dtypes; parameter counts equal to the digit: 27,781,427,952). 3.8 keeps the identical text backbone, splits its vision tower into a separate 461M projector, and ships its multi-token-prediction head as an active 65th layer. Essentially everything that improved from 3.5 to 3.8 is post-training: the thinking policy, the draft head, and the output style. On this suite, 3.8 answers equally correctly roughly 6 to 9 times faster end to end.

3.5 finds the right answer early and then spends seven times the discovery cost on loops of re-checking. 3.6 is the same policy mildly trimmed. 3.8 is a different policy altogether: near-linear derivation, one verification pass, commit. The 3.5 to 3.6 step and the 3.6 to 3.8 step are different kinds of upgrade, and only the second one changes the model's character.

04The effort dial nobody is actually turning

The community says qwen3.8 "wildly overthinks" at its default xhigh effort: 22,276 thinking tokens for one SVG drawing in Simon Willison's LM Studio test, and a Hugging Face thread titled "This model cannot stop thinking." This benchmark measured the opposite: 3.8 never exceeded 7k thinking characters. Both observations are correct. The difference is the serving stack, and it is verifiable in source.

Verified in Ollama v0.32.14 source (model/renderers/qwen35.go): Ollama never sets the official template's reasoning_effort variable. It prepends a plain English sentence to the system message. think:"low" injects "keep your thinking brief"; "medium" injects nothing; "high" and "max" inject a sentence saying effort is xhigh; think:true maps to "medium", meaning nothing at all.

Measured effect (8 problems per level): low 1,020 tokens, medium 1,115, high 600, max 662, all correct. The "xhigh" sentence makes thinking shorter, not longer. The trained deep-reasoning regime is unreachable through Ollama, so every Ollama benchmark of this model, including this one, describes the low-effort regime.

05Speed: one mechanism explains every number

Raw decode is identical across versions (78.6 to 80.4 tok/s, MTP off, paired). What differs is the multi-token-prediction draft head. Speculative decoding multiplies speed by a factor set by draft acceptance, and acceptance is set by how predictable the output is: content type, temperature, penalties, effort. The same model measures 59 to 205 tok/s depending on those conditions.

This one curve reconciles every historical figure from this machine: 171 tok/s (Aug 14 report: MTP on, temp 0.2, code-heavy suite; reproduced here as 189 on code at temp 0.2), 125.5 (Aug 16: llama.cpp MTP n=2 ladder), 96 to 104 (essay prose, acceptance ~0.36), 70 to 79 (MTP off, penalties and heat soak). No contradictions; four operating points of one mechanism. A tok/s claim without content, sampling, and MTP state attached is not a number, it is an anecdote.

07Qwen's own recommended settings can hurt

Under each model's official card settings, thinking mode: 3.5 dropped from 16/16 to 14/16. All failures were one mechanism: the card's presence_penalty 1.5 punishes the naturally repetitive structure of arithmetic verification, and thinking runs away to the token cap on the modular arithmetic problem. It even dragged 3.6 down once. On Ollama, presence_penalty 0 beat 3.5's own card, and stock ollama run qwen3.5 inherits the bad value as its Modelfile default. 3.8's card (penalty 0, think:"max") held at 16/16 with fewer tokens.

One honest caveat: through Ollama, the official xhigh deep-thinking regime is unreachable, so this comparison characterizes the low-effort regime that Ollama users actually get. Whether template-driven deep thinking buys accuracy on problems harder than this suite is the open question for the planned vLLM follow-up, which is committed to the exact same Q4_K_M GGUF files or no test at all.

09What to actually run

  • Default to qwen3.8. Same accuracy here, 6 to 9× faster in practice, 176 to 205 tok/s on structured output.
  • Leave 3.8's MTP on; it never lost. For 3.5/3.6, MTP only pays on code and structured output; it costs ~25% on prose.
  • Use presence_penalty 0 in thinking mode for all three, including 3.5, despite its card.
  • Treat Ollama's think levels as weak nudges, not the model card's effort semantics.
  • 64k context costs 8% decode and nothing in quality; 128k fits but is tight with desktop apps open.

10Method

397 runs. 8 base + 4 hard problems, every answer brute-force verified unique; graders are string extractors on a mandated ANSWER line, never LLM judges; filler text screened for answer leakage. Controls: forward + reverse model order per pass; discarded warmup after every load; VRAM fully unloaded and verified empty between models; MTP pinned per run; fixed seeds; GPU temperature, power and throttle state logged before every run; server-reported token timings. Order effect measured under 1% on decode. Limits: accuracy cells are 2 samples at temp 1.0 (fine for 7× effects, not for 1-problem gaps); one Ollama session, one machine, Q4_K_M only; ~6% cross-session drift on this rig, so all comparison tables are same-session paired. Ollama 0.32.14 showed sporadic instant HTTP 500s on the first large-prompt request after a model swap (runner IPC reset); all retried, no failed request was graded. Raw data: results.jsonl; harness: bench.py, problems.py, analyze.py; metadata: gguf_meta.json.
