DeepSeek Sparse Attention, explained with pictures

The Scout and the Library

A language model reading 128,000 tokens has to decide which earlier words matter. DeepSeek's trick is to send a cheap scout first, keep the best 2,048, and let the expensive attention read only those. Here is how it works, one picture at a time.

Chapter 1

What attention actually does

Every token in a transformer plays three roles at once. As a query it asks "who should I look at?". As a key it answers "here is what I am about". As a value it carries "here is what I would give you". All three are just learned projections of the same vector.

For one query token, the model compares its query with every earlier key, scales the scores, and runs softmax so they add up to one. The output is a weighted average of the values.

Chapter 2

Most of the attention map is dark

Stack all those rows up and you get an attention heat map. Softmax makes the weights in each row add up to one, so when a few tokens get most of the weight, everything else in that row is pushed close to zero. In long contexts, that is the usual picture: a handful of bright cells per row and a long dark tail.

That observation is the bet behind DeepSeek Sparse Attention. What if we only computed the bright cells?

Chapter 3

Why long context hurts twice

Running a model has two phases with two different bottlenecks. The numbers below are for DeepSeek-V3.2-Exp at its 128K context: 131,072 tokens, 128 attention heads, 61 transformer layers plus one multi-token-prediction layer.

Prefill: reading the prompt

Compute-bound

You build the full L by L attention matrix. At 131,072 tokens that matrix has 17.2 billion cells per head per layer. Cost grows with L squared.

Decode: writing the answer

Memory-bound

Tokens come out one at a time. To avoid recomputing the past, the model keeps a KV cache. In BF16, one 128K request holds 9.36 GB of cache across the 62 layers, and every new token must read all of it. Cost grows with L, every step.

In DeepSeek's words
DSA reduces the core attention complexity of the main model from O(L²) to O(Lk), where k is the number of selected tokens and k is much smaller than L.
Chapter 4

The catch: you cannot see the bright cells without computing them

The obvious plan is "skip the near-zero entries". The problem is that it is circular. You only find out which cells are bright by computing all of them, and computing all of them is exactly the work you wanted to avoid.

So the real question is different: can something much cheaper predict where the spikes will be, before running the full attention?

Chapter 5

DSA's answer: send a scout first

DeepSeek adds a small, fast network to every attention layer called the lightning indexer. Given the current token and all earlier tokens, it produces a rough relevance score for each of them. A top-k selector keeps the 2,048 highest. Then the real attention runs on those 2,048 only.

Each stage has one job. The scout trades precision for speed: it only needs a good ranking, not exact numbers. The selector is purely mechanical. The attention step is the same computation as before, just on a much smaller set.

What it bought
On DeepSeek's own H800 cost chart, decoding at the 128K position drops from about 2.2 to about 0.25 dollars per million tokens, and prefill from about 0.66 to about 0.19. The public API price was cut by more than half on the same day.
Chapter 6

How the scout scores a token

The indexer is deliberately small. It has 64 heads of 128 dimensions, against the main attention's 128 heads reading 576-dimensional keys. For the current token it makes 64 small query vectors and 64 scalar weights. For every earlier token it makes a single shared key, used by all 64 heads.

The score is a weighted sum, across heads, of ReLU applied to the dot product between each indexer query and that shared key. Both sides are stored in FP8. DeepSeek picked ReLU over softmax purely for throughput. The score does not need to be exact. It only needs to rank well.

Where the pieces come from

The indexer queries are projected from the same compressed query latent the main attention uses. The shared key is projected from the token's hidden state and normalised. The 64 weights are a third small projection of the hidden state. Position is added with rotary embeddings on 64 of the 128 dimensions.

0.87B

parameters across 62 layers, about 14 million per layer, on a 671-billion-parameter model. The indexer also keeps its own tiny key cache: 128 FP8 numbers per token per layer.

Why 2,048?
It is a fixed hyperparameter in the model config. It is the same budget for every query and every layer.

Chapter 8

It sits on top of MLA, and the two fix different things

DeepSeek models already use multi-head latent attention (MLA). Instead of storing full keys and values for every head, MLA stores one compressed latent per token and expands it when needed. In this model that latent is 512 numbers, plus 64 numbers that carry rotary position, so 576 numbers per token per layer. Storing full keys and values for all 128 heads would take 40,960. That is 71 times less per entry.

But MLA has a limit. It shrinks each entry in the cache. It does not reduce the number of entries. With L tokens, it still reads L latents on every decode step.

One requirement
DSA runs in MLA's multi-query mode: all 128 query heads share the same 576-number key and the same 512-number value for each selected token. Sharing is what makes fetching a small set of entries pay off, because each fetched entry serves every head.
Chapter 9

The full picture: two paths, one gate

Inside one attention block, the current token's hidden state splits into two paths. The indexer path on top is fast and disposable. The MLA path below is precise and full resolution. They meet at a gate: the index set from the top decides which cache entries the bottom is allowed to load.

Chapter 10

How it was trained: teach the scout, then unfreeze everything

DSA was not trained from scratch. It was added to a finished model, DeepSeek-V3.1-Terminus with its context already extended to 128K, through two stages of continued pre-training. The normal post-training pipeline then ran on top, unchanged from V3.1-Terminus, so any difference in results can be pinned on DSA.

Stage 1 · dense warm-up

Only the scout learns

1,000 steps of 16 sequences of 128K tokens, 2.1 billion tokens in total. Attention stays dense. Every existing weight is frozen; the new indexer is the only trainable part. Its target is the frozen model's own attention: the real attention scores are summed across all heads and normalised to a distribution, and the indexer is trained with a KL-divergence loss to match it. In plain words, the scout copies where the big model looks. Learning rate is 0.001.

Stage 2 · sparse training

Everything learns, with the budget on

15,000 steps of 480 sequences of 128K tokens, 943.7 billion tokens in total. The selector now picks 2,048 tokens per query and attention only sees those. All weights train, at a learning rate of 0.0000073. The indexer keeps its KL loss, now measured only over the selected tokens. One deliberate detail: the indexer's input is detached from the graph, so the indexer learns only from its own loss and the main model learns only from the language-modelling loss.

Did it hurt quality?
On DeepSeek's published benchmark table, V3.2-Exp lands within a few points of V3.1-Terminus in both directions: MMLU-Pro 85.0 versus 85.0, AIME 2025 89.3 versus 88.4, GPQA-Diamond 79.9 versus 80.7, HMMT 2025 83.6 versus 86.1. DeepSeek attributes the small drops to the sparse model writing fewer reasoning tokens.
Chapter 11

What it costs, honestly

The indexer still compares the current token with every past token, so its cost still grows with L squared. DeepSeek says so plainly in the report. What changed is the constant: 64 heads of 128 dimensions in FP8, against 128 heads reading 576-dimensional keys and 512-dimensional values in BF16.

The sparse attention itself is genuinely linear: 2,048 entries per query, no matter how long the context. Counting multiply-adds per query token per layer from the config gives the picture below.

Small surprise
Below about 35,000 tokens the indexer does fewer multiply-adds than the sparse attention core it feeds, because 64 × 128 per token is so small. Above that, the indexer's quadratic term is the larger of the two, which is exactly why DeepSeek flags it as the remaining O(L²) piece.
Chapter 12

On the GPU: three kernels, no detours

A mechanism that works on paper must also map to hardware. DeepSeek published the attention kernels in its FlashMLA library and the indexer scoring kernel with the model's reference code. Per layer, per token, the work is three steps.

FP8 index scoring

The 64 indexer queries, their weights, and the cached FP8 indexer keys go through one scoring kernel that returns a score for every past position.

Top-k

Keep the 2,048 highest scores, or every position if fewer than 2,048 exist yet. The result is a list of positions that points straight into the paged KV cache.

Sparse MLA attention

The kernel fetches only the listed entries, 656 bytes each in FP8, dequantises them to BF16, and runs the 128-head attention in BF16 on chip.

The hard part was not the maths
DeepSeek's own kernel write-up shows the decode kernel is dequantisation-bound: on an H800, turning one token's FP8 entry back into BF16 takes about 50 clock cycles on the CUDA cores, while the tensor-core multiply for 64 query heads takes about 34. Their fix, nicknamed "crossover", has two thread blocks share dequantised entries through Hopper's distributed shared memory so each block only converts half.
Chapter 13

Two kinds of sparsity in one model

The model was already sparse before DSA. It keeps the DeepSeek-V3 skeleton: a mixture-of-experts model with 671 billion parameters in total and 37 billion active per token, because the router picks 8 of 256 routed experts, plus one shared expert that is always on. DSA adds a second, independent kind of sparsity: which past tokens to attend to.

Both are learned and both depend on content. Neither is fixed, and neither is positional.

Chapter 14

Where it still hurts

DSA is a real win, and it has real limits. These follow from the report, the config, and the kernel code.

The scout is still quadratic

The report says it directly: the lightning indexer still has O(L²) complexity. The constant shrank a lot, but the scaling law did not change.

A miss is permanent

Attention is computed only over the top-k set. If the indexer leaves out a token that would have mattered, that token is invisible for this query at this layer. There is no second pass.

Gather plus dequantise is the bottleneck

DeepSeek's kernel write-up calls the sparse memory access and the FP8-to-BF16 conversion the hard parts, and had to invent a cross-block sharing trick to keep the tensor cores busy.

One budget for everyone

Top-k is a single number, 2,048, for every query, every layer, every task. Some queries need far fewer tokens. Some might genuinely need more.

Hardware specific

DeepSeek's sparse kernels target NVIDIA Hopper and Blackwell. Other vendors maintain their own ports, and the Blackwell decode kernel is described as not yet optimised.

Still labelled experimental

The report itself says DeepSeek is pursuing further large-scale real-world testing to uncover potential limitations of the sparse architecture.

Chapter 15

The whole story in one breath

  1. Attention is expensive at long context because every token checks every other token. That is quadratic, and it also drags the whole KV cache through memory on every decode step.
  2. But most of those checks are wasted. In each row, a few tokens take most of the weight and the rest sit near zero.
  3. You cannot skip the zeros without computing them first, so DSA predicts them instead: a 64-head FP8 indexer, under a billion parameters in total, scores every past token cheaply.
  4. A selector keeps exactly 2,048 tokens per query. At the 131,072-token context, that is 1.56 percent.
  5. Full-quality attention runs only on those 2,048. MLA had already made each cache entry small; DSA makes the number of entries read small.
  6. The scout learned by copying a frozen model's attention for 2.1 billion tokens, then the whole model trained with the budget on for 943.7 billion. Benchmarks stayed level, and DeepSeek's decode cost at 128K fell by roughly nine times.
